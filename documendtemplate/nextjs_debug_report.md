 # Next.js 14 移行プロジェクト：開発サーバー起動問題 デバッグレポート

## はじめに

このレポートは、Next.js 14への移行プロジェクトにおいて発生した、開発サーバーが起動しないという深刻な問題の解決に至るまでの全記録です。問題の特定から解決、そして将来の予防策までを網羅し、今後の開発における貴重なナレッジとして活用することを目的とします。

---

### ① どのようなエラーが発生していたか (発生した問題)

プロジェクトが直面した問題は、単一ではなく、複数の要因が複雑に絡み合った連鎖的なものでした。

1.  **原因不明のサーバークラッシュ:** `npm run dev`を実行すると、Next.jsが設定ファイルを読み込む非常に早い段階でクラッシュ。ターミナルには断片的なログしか表示されず、直接的な原因特定が困難でした。
2.  **依存関係と型定義の不整合:** `package.json`の内容が破損しており、`styled-components`や`@types/react`などで型エラーが頻発。依存関係のクリーンインストールを繰り返しても解決しませんでした。
3.  **設定ファイルの競合:** Next.jsの標準ではない`eslint.config.mjs`が存在したことで、設定の読み込み時に内部的な競合が発生していました。
4.  **TypeScriptコンパイル問題:** すべての競合を解消した後も、`next.config.ts`というTypeScript形式の設定ファイルが存在するだけでサーバーがクラッシュする、という不可解な問題が残りました。
5.  **ビルドエラー（フォント不足）:** サーバー起動後、`layout.tsx`で指定された`Geist`フォントがプロジェクトにインストールされていなかったため、最終的なビルドに失敗していました。

### ② 考えられる対策として何をしたか (実行した対策)

問題解決のため、以下の対策を段階的に実行しました。

-   **依存関係の完全リセット:** `node_modules`, `package-lock.json`の削除と`npm cache clean --force`による、依存関係の完全なクリーンアップ。
-   **`package.json`の再構築:** 破損していた`package.json`を削除し、互換性のあるバージョンで手動で再作成。
-   **設定ファイルの段階的な無効化:** 問題の切り分けのため、`next.config.ts`, `tailwind.config.ts`, `postcss.config.mjs`, `eslint.config.mjs`を一つずつ無効化し、サーバーの起動を試すことで、問題のあるファイルを特定する「二分探索」的なアプローチを取りました。
-   **デバッグログの取得:** `npm run dev -- --debug`や`npm run dev > debug.log 2>&1`といったコマンドで詳細なエラーログの取得を試みましたが、文字化けやログの途切れにより失敗しました。
-   **設定ファイルの形式変更:** 問題が`next.config.ts`にあると特定した後、TypeScriptのコンパイル問題を疑い、同等の内容を持つJavaScript形式の`next.config.js`に置き換える、という最終手段を実行しました。
-   **不足パッケージのインストール:** 最後のビルドエラーに対し、エラーメッセージに従い`geist`フォントパッケージをインストールしました。

### ③ 結果、何が問題解決に至ったのか (根本原因と解決策)

連鎖的な問題の根本原因と、それぞれの最終的な解決策は以下の通りです。

-   **主原因（サーバークラッシュ）:** **Next.jsが`next.config.ts`をコンパイルする過程の潜在的な不具合。**
    -   **解決策:** ファイルを**`next.config.js`というJavaScript形式に置き換える**ことで、TypeScriptのコンパイル処理を回避し、問題を根本的に解決しました。
-   **副原因（ビルドエラー）:** **`Geist`フォントの未インストール。**
    -   **解決策:** `npm install geist`を実行し、必要なフォントをプロジェクトに追加しました。

### ④ いち早く解決に至るためのナレッジ (今後のための学び)

今回の経験から得られた、将来のトラブルシューティングを迅速化するための重要な教訓は以下の通りです。

1.  **「不可解なクラッシュ」は設定を疑う:** エラーログが不十分なままサーバーが即座にクラッシュする場合、コード本体よりも、フレームワークが読み込む**設定ファイル（`next.config`, `postcss.config`など）の競合や、構文・形式の問題**を第一に疑うべきです。

2.  **「最小構成」で切り分ける:** 問題が複雑に見える時こそ、一度すべてのカスタム設定を無効化し、**「フレームワークのデフォルト状態で動くか？」**を確認するアプローチが極めて有効です。そこから一つずつ設定を元に戻すことで、原因箇所を確実に特定できます。

3.  **ファイル形式を疑う:** 特にTypeScriptを利用している場合、`.ts`ファイルで原因不明の問題が起きたら、一度**`.js`形式に書き換えてみる**ことで、「コードの内容」が問題なのか、「TypeScriptのコンパイル過程」が問題なのかを素早く切り分けることができます。

4.  **規約に従う:** Next.jsのようなフレームワークは、標準的なファイル名やディレクトリ構成に強く依存しています。`eslint.config.mjs`のような**非標準のファイルは、意図せぬ競合の原因**となり得ます。公式ドキュメントで推奨される構成を維持することが、安定動作の鍵となります。

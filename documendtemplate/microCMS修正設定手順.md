MicroCMSデータとTypeScript型の一致検証・修正手順書
目的: MicroCMSからのAPIレスポンスと、TypeScriptの型定義の間に存在する不一致を特定し、修正することで、データの型安全なパースと表示を実現する。

前提:

MicroCMSのAPIキー、サービスドメインは正しく設定されている。
ブラウザのデベロッパーツール（Networkタブ）で、対象APIエンドポイントへのリクエストが ステータスコード 200 (OK) で成功していることを確認済み。
しかし、コンソールには FetchError が表示され、データが期待通りに処理されていない。
Step 1: 【情報収集】実際のAPIレスポンス（生データ）を取得する
目的: MicroCMSサーバーが実際に返しているJSONデータの正確な構造を把握する。

手順:

ブラウザで問題が発生しているページ（例: /ai/list）を開きます。
デベロッパーツールを開き、「Network」タブを選択します。
ページを再読み込みし、MicroCMSへのAPIリクエスト（例: capabilities?limit=100、GETメソッドのもの）を探します。
該当のリクエストを選択し、「Response」タブまたは「Preview」タブを開きます。
表示されたJSONデータ全体、特に contents 配列内の最初の1つか2つのアイテム（オブジェクト） をテキストエディタなどにコピー＆ペーストして保存します。これが「正解」のデータ構造です。
ポイント: totalCount や limit などのメタデータも重要ですが、型不一致の主な原因は contents 配列内の個々のアイテムの構造にあります。
Step 2: 【情報収集】現在のTypeScript型定義を確認する
目的: プロジェクト内でMicroCMSのデータを扱うために定義されているTypeScriptの型（interfaceやtype）を確認する。

手順:

プロジェクト内の型定義ファイル（例: 
src/types/index.ts
 や src/types/microcms.ts など）を開きます。
今回のAPIエンドポイント（例: capabilities）のデータを格納するための型定義（例: 
AICapability
）を見つけます。
その型定義、およびそれが参照しているカスタム型（例: 
Category
, Technology, MicroCMSImage など）のコード全体をコピーして、別のテキストエディタなどに保存します。これが「検証対象」の型定義です。
Step 3: 【比較・分析】生データと型定義を徹底比較する
目的: Step 1で取得した「正解のデータ構造」と、Step 2で取得した「検証対象の型定義」を突き合わせ、不一致箇所をすべて洗い出す。

手順:

フィールド名の比較:
JSONデータのキー名と、型定義のプロパティ名が完全に一致しているか（大文字・小文字、ハイフンとアンダースコアの違いなど）確認します。
不一致例: JSON {"created_at": "..."} vs 型定義 createdAt: string;
データ型の比較:
各フィールドについて、JSONデータの実際の値の型（文字列、数値、真偽値、オブジェクト、配列、null）と、型定義で指定されている型が一致しているか確認します。
不一致例:
JSON {"age": null} vs 型定義 age: number; （→ age: number | null; にすべき）
JSON {"tags": "tag1"} vs 型定義 tags: string[]; （→ データが単数文字列なら型を string に、データが配列ならCMS側のデータ形式を確認）
必須/オプショナルプロパティの比較:
型定義で必須（? が付いていない）プロパティが、JSONデータに常に存在するか確認します。一部のアイテムにしか存在しないフィールドは、型定義でオプショナル（?:）にする必要があります。
不一致例: 型定義 thumbnail: MicroCMSImage; vs JSONデータに thumbnail がないアイテムがある （→ thumbnail?: MicroCMSImage; にすべき）
オブジェクト/配列構造の比較:
ネストされたオブジェクトや配列の構造が、型定義とJSONデータで一致しているか確認します。
不一致例: JSON {"author": {"name": "Taro"}} vs 型定義 author: string; （→ author: { name: string; }; のようなネストした型定義が必要）
MicroCMS特有のフィールド:
画像 (image): 通常 {"url": string, "height"?: number, "width"?: number} という構造です。型定義がこれに合っているか。
日付 (createdAt, updatedAt など): ISO 8601形式の文字列 (string) です。
リッチエディタ: HTML文字列 (string) です。
関連コンテンツ: 関連先のコンテンツのオブジェクトまたはその配列です。その内部構造も確認します。
繰り返しフィールド: 配列です。その要素の型も確認します。
比較時のコツ:

JSONデータと型定義を並べて表示し、1フィールドずつ指差し確認するくらいの気持ちで丁寧に行います。
最初は contents 配列の最初の1アイテムで比較し、問題がなければ2つ目、3つ目と確認範囲を広げます（データによって構造が微妙に異なる場合があるため）。
JSON Formatter & Validator のようなツールでJSONデータを整形すると見やすくなります。
Step 4: 【修正】TypeScriptの型定義を修正する
目的: Step 3で特定した不一致箇所に基づいて、TypeScriptの型定義を実際のデータ構造に合わせる。

手順:

Step 3で見つかったすべての不一致点について、型定義ファイル（例: 
src/types/index.ts
）を修正します。
フィールド名が異なる場合 → 型定義のプロパティ名をJSONに合わせる。
データ型が異なる場合 → 型定義の型をJSONの実際の型に合わせる（例: string | null, string | number など）。
必須プロパティがデータに存在しない場合 → 型定義でオプショナル（?:）にする。
構造が異なる場合 → 型定義の構造をJSONに合わせる（ネスト構造の修正など）。
修正の優先順位: まずは FetchError が解消されることを目指し、最も怪しいと思われる箇所から修正します。
保存して再確認: 型定義を修正したらファイルを保存し、再度ブラウザでページをリロードして FetchError が消えるか、表示が改善されるか確認します。
まだエラーが出る場合は、Step 3に戻り、見落としがないか再度比較します。
エラーメッセージが変化した場合は、新たな手がかりになる可能性があります。
Step 5: 【動作確認】表示と機能の最終確認
目的: 型の不一致が解消され、データが正しく表示・利用できることを確認する。

手順:

FetchError がコンソールから消えたことを確認します。
ページ上のデータ（カード、テキスト、画像など）が期待通りに表示されていることを確認します。
データを利用する機能（フィルタリング、ソート、詳細ページへのリンクなど）が正しく動作することを確認します。
この手順に従って、現在の 
AICapability
 の問題に取り組んでみましょう。
